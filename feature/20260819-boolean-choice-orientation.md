# Part I — Business description

*Audience: clinical authors, guideline developers, implementers.*

## 1. What this is

Yes/no questions in a TRICC diagram (`select_yesno`, and a `select_one` whose two options
are a yes/no pair) already export to openSRP as a native FHIR `boolean` item. The
openSRP questionnaire renderer then lays that item out with its default boolean widget
(typically a stacked switch/checkbox). For clinical forms, Yes and No should sit **side
by side**, the same way a two-option radio question does.

This change adds a standard FHIR rendering hint to those questions so the openSRP app
draws them horizontally:

```json
{
  "url": "http://hl7.org/fhir/StructureDefinition/questionnaire-choiceOrientation",
  "valueCode": "horizontal"
}
```

No change to how authors draw the question, and no change to the captured answer
(`true` / `false`). Only the on-screen layout of Yes/No changes.

## 2. Who is affected

Clinicians filling openSRP/FHIR-Core forms generated by TRICC. Hidden logic flags
(calculates, diagnoses, waits) are not shown, so they are unaffected.

## 3. Benefits

- Yes/No reads as a pair of choices rather than a toggle.
- Matches the layout already used for other short radio lists in the same app.

## 4. Limitations

- **OpenSRP export only.** Generic FHIR SDC export is unchanged.
- **Always horizontal.** There is no authoring control to pick vertical (or to opt out)
  in this change.
- **Visible yes/no questions only.** Hidden boolean items (calculates, proposed
  diagnosis, rhombus, wait, bridge) do not get the hint — they are not rendered.
- **Not applied to multi-option `select_one` / `select_multiple`.** Those stay as
  choice items with their existing radio/checkbox item-control extensions.

# Part II — Technical specification

*Audience: developers.*

## 1. Emission rule

When `OpenSRPStrategy` builds a Questionnaire item:

| Condition | Emit `questionnaire-choiceOrientation` = `horizontal`? |
|-----------|--------------------------------------------------------|
| Item `type` is `boolean` **and** the item is **not** hidden | Yes |
| Item `type` is `boolean` **and** hidden (`questionnaire-hidden`) | No |
| Item `type` is anything else (`choice`, `integer`, `group`, …) | No |

Covered TRICC sources of a visible boolean item:

- `TriccNodeType.select_yesno` (already mapped to FHIR `boolean`)
- `select_one` rewritten to `boolean` by `FHIRStrategy._is_yesno_boolean_select`

The extension URL and value are fixed:

- URL: `http://hl7.org/fhir/StructureDefinition/questionnaire-choiceOrientation`
  (already declared as `SDC_EXT_CHOICE_ORIENTATION` in
  `tricc_oo/converters/fhir/questionnaire_item_mapper.py`; currently unused)
- `valueCode`: `"horizontal"`

This is a rendering hint only. Extraction, CQL, FHIRPath, StructureMap, and
`answerOption` emission are unchanged.

## 2. Pipeline / code checklist

- [x] `questionnaire_item_mapper.py` — add `build_choice_orientation_extension(orientation="horizontal")`
- [x] `FHIRStrategy` (`fhir_form.py`) — hook so a subclass can contribute extra extensions
      for a visible boolean item (default: none), called from `generate_base` after
      `fhir_type` / `hidden` are known
- [x] `OpenSRPStrategy` (`opensrp.py`) — return the horizontal orientation extension
      from that hook
- [x] Tests — visible yes/no on `OpenSRPStrategy` has the extension; hidden boolean
      does not; `FHIRStrategy` does not emit it
- [x] Docs — `docs/desing/FHIRcore.md` mapping-table note; `docs/open-srp-export.md`;
      `docs/tricc-elements.md` `select_yesno` bullet

## 3. Tests

New test file `tests/test_strategies/test_fhir_choice_orientation.py` (or a class on
`test_opensrp_strategy.py`):

1. `TriccNodeSelectYesNo` through `OpenSRPStrategy.generate_base` → item `type` is
   `boolean` and the extension is present with `valueCode == "horizontal"`.
2. A yes/no-style `select_one` (`_is_yesno_boolean_select`) through OpenSRP → same.
3. A hidden boolean (calculate, or a node that gets `questionnaire-hidden`) through
   OpenSRP → extension **absent**.
4. The same `select_yesno` through `FHIRStrategy` → extension **absent**.
5. A non-boolean `select_one` (e.g. sex male/female) through OpenSRP → extension
   **absent**.

## 4. Acceptance criteria

- Visible yes/no questions in an `OpenSRPStrategy` Questionnaire carry exactly the
  extension shown in Part I.
- Hidden booleans and non-boolean items do not.
- `FHIRStrategy` export is unchanged.
- Captured values remain native boolean `true`/`false` (no `answerOption` list).
- Existing OpenSRP / FHIR tests still pass.

## 5. Out of scope

- Author-configurable orientation (`display_type` or similar).
- Applying the extension to `choice` / `open-choice` items.
- Changing the boolean widget via `questionnaire-itemControl` (radio-button vs
  switch). If the openSRP renderer also needs `itemControl` to honour orientation,
  that is a follow-up.
- XLSForm / CHT / OpenMRS output.
